# Encrypted findings journal V1

This is a trusted-backend filesystem storage foundation. It is not an enabled service, database migration, authorization endpoint, UI, independent witness service or chain anchor. All root paths, crypto/signing objects, key allowlists, officer scope and expected tips must be supplied by backend configuration. Never expose these methods directly to request-supplied objects.

## Stored records

`append_receipt` recovers an existing private `PROTECTED_OBSERVED_CONTRADICTIONS` receipt with primary and backup keys, checks its artifact/policy binding, officer scope, reported-only flags and result digest, and stores the complete decrypted finding inside a new encrypted signed entry. Receipt bytes receive a SHA256 pin. The full embedded query/comparison preserves source references, claim/version IDs, effective date, knowledge time, reasons, exclusions, coverage, journal/checkpoint/witness pins and original provenance. An entire comparison run is one finding version; it may contain zero, one or multiple comparison pairs. Empty comparisons never establish absence of contradiction.

This step supports contradiction-run receipts only. Authority and reconstruction findings adapters remain pending. Recovery of an old receipt authenticates its encryption binding; it does not redo anchored replay, current live readiness or current witness freshness. The recorded `authenticated_journal_replay` field describes the producer's original execution, not a new storage-side verification. Trusted source-runner capture integration remains pending.

`finding_id` is a backend-assigned UUID stable across that finding's corrections. `operation_id` is a separate backend-assigned UUID for retries. A correction appends a new full receipt with the same finding ID, a nonempty explanation and `supersedes` equal to the current finding entry's ciphertext digest. Original files are preserved. A new finding cannot reuse an existing finding ID. Review entries do not become finding heads; a correction links to the most recent finding/correction, while the global entry hash chain includes all reviews. Stable IDs and chain pins stay inside encrypted payloads except the opaque ledger UUID, sequence and externally retained ciphertext tip.

## Reviews

`issue_review_intent` is internal trusted-review backend code. Separate pinned Ed25519 reviewer keys sign the exact ledger/officer/finding/current-head digest, operation, decision, explanation, evidence references and issuance/expiry times. `append_review` verifies that signature, scope and current finding head, and that the journal recorder's timestamp lies inside the review window. Review validity on later replay is checked at its original recording instant; expiry does not erase a recorded review. Concurrent stale-head review/correction attempts are refused.

Allowed reported decisions are `NEEDS_MORE_EVIDENCE`, `REPORTED_DISAGREEMENT_SUPPORTED`, and `REPORTED_DISAGREEMENT_NOT_SUPPORTED`. These are reviewer assertions, not accepted officer state. Key allowlisting establishes signer identity in this configured domain, not action-date SP/OIC authority, delegation, jurisdiction or scoped UI access. That authorization integration is pending. `evidence_references` records review rationale references; this storage layer does not authenticate their custody.

## Integrity, retry and recovery

Each entry is domain-separated, writer-signed and AEAD-encrypted. The signature covers policy, ledger/officer scope, sequence, previous ciphertext SHA256, operation, finding lineage, local UTC recording time and payload. Signing keys are separate from encryption/lookup keys; writer and reviewer public-key sets must be disjoint. Keep all historical verification/decryption keys required for replay. This step does not provision keys or implement rotation management.

`FindingsJournal` requires an existing owner-only directory outside the repository. Artifact files have mode 0600, exclusive non-overwriting publication and fsync. Advisory directory locking serializes cooperating writers. No update/delete method exists. Appends and reads replay the entire signed/encrypted chain against an explicit expected tip `{ledger_id, sequence, entry_sha256}`. Recording times come from the recorder's current aware UTC clock and must strictly increase, never from CSV effective dates. Clock rollback blocks new writes.

Expected tips must come from independently protected, durable trusted storage. Do not derive them from this directory's latest filename, silently reset to `empty_tip`, or retain them only in volatile memory. `empty_tip()` is a convenience for a separately provisioned new ledger UUID; it does not authorize clearing an existing ledger. The module checks inventory, signatures, lineage and final digest against the supplied tip; an old-but-fully-replayed ledger cannot be detected if an attacker can also roll back that external pin. Filesystem append-only API discipline is not OS-level WORM storage: an owner can delete files. Operational witness/tip integration is pending.

A matching operation/content retry against the current independently committed tip returns `ALREADY_RECORDED`; changed retry content is refused. A stale expected tip is refused even for an old operation. The external tip must be updated by the trusted controller after publication; no atomic cross-store transaction is claimed. Publication or directory-fsync failure may leave one complete signed encrypted entry without an external tip update. `recover_pending` requires the old independent tip, exact operation ID and explicitly approved pending ciphertext digest, verifies precisely one additional complete entry, and returns the recovered tip. It does not choose a local latest tip or update any external service. No automatic recovery/deletion occurs. Interrupted encrypted staging files with prefix `.observation-` are not ledger entries and are ignored; their cleanup requires trusted maintenance. Other unexpected inventory is refused.

`read` returns sensitive plaintext to authorized backend code only. Do not print it or pass it to an unscoped UI. Append/recovery summaries expose status and opaque ciphertext tip only; accepted state remains null and findings_anchored remains false. This module creates no on-chain commitments; salted HMAC findings commitments and both-chain anchoring remain pending.

## Development validation

Disposable encrypted fixtures test full receipt/provenance/reason preservation including an actual reported candidate, correction history and restart, signed reviews, expired/future/stale/tampered reviews, retries, writer/reviewer separation, private paths, inventory drift, rollback, matching-file-pin signature tampering, concurrent stale writers, interrupted publication with explicit recovery, and clock/fsync failures. Existing protected comparison/query and pure contradiction regression suites accompany these tests. Source loader/readiness boundaries remain fixtures; this is not live research validation.

No research schema, intake hook, findings service, production key or witness service is provisioned. Existing CSVs, research databases, original anchors and chain state are unchanged. RPC 1 remains deferred. Independent research evaluation remains pending.
